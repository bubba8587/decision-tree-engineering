## Decision

The ID letter is the ring and numbers are never reused, as before. There
are no aliases. Moving a node to another ring creates a new node with a new
ID in that ring, marks the old node `superseded` by it, and rewrites every
citation and every child's `parents` to the new ID in the same change. The
old file stays. A node file is never renamed or deleted.

## Why

The owner, after a review of alias behaviour on 2026-09-02: "I think I
don't want to allow aliases."

The review found that aliases undermined the two things they were meant to
serve. B2 kept the old ID resolving so that a citation would never point at
nothing, but a lingering `dte:C4` then read as ring C while resolving to
ring B, so the ID lied about precedence, which is the one thing A1 needs
the ID to be honest about. And because a move was file-level a rename, an
agent could pull a shallower node into its own ring by recreating it with
an alias, and the ring check saw only a change at the agent's ring.

Treating a move as a supersession fixes both without new machinery. The
old file stays, so its number stays reserved and the demotion has to touch
a file at the shallower ring, which the authority check sees. Citations are
rewritten by the tool rather than left to resolve later, so no ID ever
means two things.

## Consequences

- `aliases` is not a field. Its presence is an error.
- `dte move <ID> <ring>` performs the whole operation (C9).
- A citation to a superseded node is a warning, as for any retired node.
- Deleting or renaming a node file is an error when git can see it (C10),
  which is also the first enforcement of B5.
- B11 still protects human-held nodes: moving one requires `authorized_by`.
